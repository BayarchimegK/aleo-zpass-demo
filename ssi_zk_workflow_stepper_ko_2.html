A 단계 — 자격증명 발급
발급자는 보유자가 제출한 'commitment'에 대해 서명하고, 레지스트리에 필요한 SSI 필드(`commitment`, `issuerSignature`, `holderDID`, `isAdult` 파생값)를 저장합니다.
보유자
브라우저/지갑
1
VC 발급 요청
사용자가 브라우저 또는 지갑을 통해 발급자 UI에 VC 발급을 요청합니다.
발급자 UI
VC 발급
2
서명된 VC 반환
발급자가 VC를 생성하고 서명한 뒤 사용자에게 반환합니다.
3
레지스트리에 VC 등록
발급자 백엔드는 보유자가 제공한 commitment에 대해 서명(`issuerSignature`)하고, 레지스트리에 `commitment`, `issuerSignature`, `holderDID` 및 파생된 `isAdult` 값을 저장합니다.
인증 백엔드
레지스트리
B 단계 — 인증
보유자가 VC와 nonce(또는 VC 관련 material)를 제출하면 인증 백엔드가 저장된 commitment와 대조하여 vcSignature를 검증하고, 폐기여부를 확인한 뒤 nullifier를 기록하여 단기 JWT(credentialId, isAdult 포함)를 발급합니다.
보유자
브라우저/지갑
4
VC 제출
보호된 콘텐츠 접근을 위해 보유자가 자신의 VC를 인증 백엔드에 제출합니다.
인증 백엔드
VC 검증
5
단기 JWT 발급
인증 백엔드는 제출된 VC material과 nonce로부터 vcSignature를 검증하고(저장된 commitment와 대조), revocation 체크를 수행한 뒤 nullifier를 로그에 남깁니다. 이후 `credentialId`와 `isAdult`를 포함한 단기 JWT를 발급하여 반환합니다.
C 단계 — Zero-Knowledge 증명 생성
Aleo 기반 ZK 증명을 클라이언트에서 WASM으로 생성하도록 설계됩니다. 서버는 데모용으로 `AleoService.verifyProofOutput()`를 통해 증명 출력에서 `isAdult`를 도출할 수 있지만, 운영 환경에서는 클라이언트 측 WASM 증명 생성이 권장됩니다.
보유자
WASM 실행
6
ZK 증명 생성 요청
사용자가 Aleo ZK 회로를 호출합니다. 클라이언트 환경에서 WASM 기반으로 직접 증명을 생성합니다.
Aleo / 증명자
ZK 회로·WASM
7
증명 결과 반환
클라이언트에서 WASM으로 증명을 생성하면 opaque ZK proof가 반환됩니다. 서버(데모)는 `AleoService.verifyProofOutput()`로 proof 출력을 파싱하여 `isAdult`를 유도할 수 있으나, 프로덕션은 가능한 한 클라이언트에서 증명을 생성·검증하도록 설계해야 합니다.
D 단계 — 콘텐츠 접근
콘텐츠 백엔드는 단기 JWT를 검증하고 실시간으로 폐기(revocation) 상태를 확인하여 접근을 허용합니다. 현재 구현은 콘텐츠 백엔드가 raw ZK proof를 재검증하지 않아도 동작합니다(검증은 인증 단계에서 수행되어 JWT가 발급됨).
보유자
브라우저/지갑
8
JWT 전달 및 revocation 확인
보유자는 단기 JWT(및 필요 시 opaque proof)를 콘텐츠 백엔드에 제출합니다. 콘텐츠 백엔드는 JWT 유효성 검사 후 인증 백엔드의 revocation 엔드포인트를 호출하여 실시간 폐기 여부를 확인합니다.
콘텐츠 백엔드
검증자
9
접근 허용 / 거부
검증 결과에 따라 사용자에게 콘텐츠 접근을 허용하거나 거부합니다.

검증 책임: 콘텐츠 백엔드가 raw ZK proof를 재검증하려면 (a) 증명을 포워드하거나 (b) 콘텐츠 백엔드가 `/auth/verify`로 proof를 요청하도록 변경해야 합니다.
운영 권장: 클라이언트 측 WASM으로 증명 생성; 서버는 audit/추적용으로 proof 메타만 저장.
